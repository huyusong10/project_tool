## 目标

在保留 React、Fastify、SQLite、REST 和 MCP 的前提下完成渐进式重构。

- 服务端按业务领域组织，HTTP 和 MCP 复用同一组业务函数。
- 前端明确页面、业务模块和基础设施的职责。
- 统一 API 契约、写入结果重查和缓存失效规则。
- 缩短日常验证时间，保持数据和旧客户端兼容。

本轮不引入微服务，不全面改写 ORM，不同时更换状态管理和 UI 框架。

## 当前约束

- 当前工作区有大量未提交改动。开始重构前先形成可还原基线，避免把功能改动和结构迁移混在同一批次。
- 模块拆分阶段不修改数据库结构、HTTP 路径、MCP 工具名和业务行为。
- 每个批次只迁移一个领域或一种公共机制。批次结束时可以独立发布和回退。
- 旧数据迁移、访客访问隐藏项目存在性的 404 语义、写入版本检查和审计记录必须保留。

## 目标边界

```text
client/pages ──> client/features ──> client/core
       │                │                 │
       └────────────────┴──────> shared <─┘

server/http ─┐
             ├──> server/services ──> server/database
server/mcp ──┘             │
                            └────────> shared
```

依赖规则：

- `shared` 只放类型、校验、纯规则和纯计算，不访问浏览器、Fastify 或数据库。
- 页面负责路由、布局和当前对象选择，不直接拼接接口地址。
- 业务模块负责查询、命令、缓存更新和业务 UI。
- HTTP 与 MCP 负责输入、权限和输出映射，不实现业务规则。
- 服务之间禁止循环依赖。

## R1：服务端领域拆分

### R1.1 消除现有循环依赖

先处理 `services.ts`、`delivery-execution.ts`、`milestones.ts` 之间的循环。

- 把共享查询和状态计算移动到无反向依赖的模块。
- 业务函数通过参数接收所需查询或上下文。
- 不建立新的全局服务容器。

验收：依赖扫描没有服务端循环，现有交付和里程碑测试通过。

### R1.2 迁移业务领域

按以下顺序从 `src/server/services.ts` 迁移：

| 顺序 | 领域 | 主要内容 |
|---|---|---|
| 1 | projects | 项目、成员、访问范围 |
| 2 | templates | 模板、模板实例化 |
| 3 | requirements | Feature、Phase、需求、归属 |
| 4 | work-items | 工作项、负责人、排序、进展 |
| 5 | delivery | 交付执行、里程碑、完成规则 |
| 6 | archive | 归档、恢复、兼容检查 |

每次迁移执行相同步骤：

1. 为现有行为补充特征测试。
2. 移动查询和命令，不改接口和 SQL 语义。
3. 让现有导出转发到新模块，保持调用方可用。
4. 迁移 REST 路由。
5. 迁移对应 MCP 工具。
6. 删除旧实现并运行领域测试和完整 Vitest。

目标文件职责：

- `src/server/services/<domain>.ts`：查询、命令和事务。
- `src/server/*-routes.ts`：HTTP Schema、权限和结果映射。
- `src/server/mcp-tools/<domain>.ts`：MCP Schema、权限和结果映射。
- `src/server/routes.ts`、`src/server/mcp.ts`：只注册模块。

### R1.3 收敛数据库访问

- 提供显式数据库上下文，先保留现有单例兼容入口。
- 新迁移的服务通过参数取得数据库连接。
- 测试直接创建隔离数据库，不依赖动态导入顺序。
- 暂不把原生 SQL 全面改写为 Drizzle。

### R1 验收

- `services.ts` 不再保存业务实现，只保留兼容导出；调用方迁完后删除兼容层。
- `routes.ts` 和 `mcp.ts` 不包含业务判断。
- REST 与 MCP 的同一操作调用同一个业务函数。
- 服务端没有依赖环。
- 数据库迁移文件和现有 HTTP、MCP 契约没有变化。

## R2：客户端契约与写入流程

### R2.1 建立领域 API

逐领域建立 `src/client/features/<domain>/api.ts`：

- 封装路径、请求和响应类型。
- 页面和组件不再直接调用字符串形式的 `/api/...`。
- 请求与响应 DTO 放在 `src/shared` 对应领域模块。
- 对高风险响应增加运行时校验，普通列表先保持静态类型。

迁移顺序与服务端一致。每迁完一个领域，删除 `src/client/types.ts` 中对应的重复类型。

### R2.2 统一写入结果重查

建立一个小型写入流程：

```text
提交成功 ───────────────> 更新缓存
   │
   └─ 网络结果未知 ─────> 保存原请求 ─> 查询正式数据 ─> 领域函数判断结果
```

公共层负责：

- 保存待核对请求。
- 控制核对状态和重试查询。
- 区分成功、未生效、冲突和无权访问。

领域层负责：

- 判断正式数据是否与原请求一致。
- 决定需要失效或直接更新的查询。
- 生成用户可读的结果说明。

先迁移账号、项目设置、交付操作，再迁移需求和工作项编辑。

### R2.3 缩小缓存失效范围

- 查询键归属到对应领域。
- 每个命令列出受影响的实体和聚合视图。
- 优先直接更新单个实体；只有聚合含义变化时才失效仪表盘和路径分析。
- 删除跨领域的全量失效调用。

### R2 验收

- 页面和展示组件不直接拼接接口路径。
- 写入结果未知的交互和保留输入行为不变。
- 同一种重查状态不再由多个页面重复实现。
- 查询失效由命令模块声明并有测试。

## 批次控制

每个重构批次包含以下内容：

| 项目 | 要求 |
|---|---|
| 范围 | 一个领域或一种公共机制 |
| 行为 | 默认不改变；行为变化单独提交 |
| 数据 | 模块迁移不附带数据库迁移 |
| 测试 | 先补特征测试，再移动代码 |
| 回退 | 保留旧导出直到调用方迁完 |
| 说明 | 记录移动范围、契约变化和验证结果 |

发现以下情况时停止当前批次：

- 需要修改不相关领域的数据结构。
- 需要同时替换多个基础设施。
- 无法说明旧行为或缺少可复现测试。
- 当前失败无法判断来自重构还是未提交功能改动。
