# 需求安排草稿与人工发布（需求草案）

## 目标与定位

Agent 通过 MCP 将原始要求整理成可审核的交付方案，人类在系统中增删改、检查拓扑及计划，然后发布。

草稿按项目保存一整份方案：来源条款、需求、工作项、工作流、依赖和计划。它是发布前的工作区，不增加需求与工作项之间的管理层级。

| 对象 | 含义 | 对正式项目的影响 |
|---|---|---|
| 草稿 | 尚未发布的方案，可以缺信息、有待解决的问题 | 不计入正式需求、工作量、甘特、预测、人员负载或承诺 |
| 已发布的候选需求 | 已进入项目，尚未纳入本期交付 | 按现有候选与完整网络规则处理 |
| 已纳入本期交付的需求 | 人类确认的交付范围 | 按现有执行、预测及验收规则处理 |

发布默认生成候选需求。人类可以明确纳入本期交付；发布不自动开工、生成实际进度、验收或记录交付承诺。

## 当前基础

现有导入页已支持来源与需求映射、合并拆分、工作项增删和导入预览，但草稿仅保存在本机 localStorage。拓扑编辑器也有本机草稿。现有导入包不包含完整计划、里程碑和工作流方案，不能只增加一个“保存草稿”按钮就完成本需求。

复用现有导入校验、实体批次、拓扑编辑及排期服务，增加服务端草稿存储和统一编辑入口。正式发布继续走现有业务服务，不绕过权限、版本和执行约束。

## 草稿流程

```text
Agent／人类创建 → 编辑中 → 提交审核 → 待审核 → 人类编辑、校验 → 发布
                   ↑                    │
                   └──── 退回及说明 ────┘
编辑中／待审核 → 关闭
```

| 状态 | 操作 |
|---|---|
| 编辑中 | 作者可保存、修改及提交审核；项目经理可查看和修改 |
| 待审核 | 经理可以直接增删改并发布，也可说明原因后退回；Agent 不继续覆盖这份方案 |
| 已发布 | 只读，保留发布版本、发布人、时间和正式对象映射 |
| 已关闭 | 不再发布，保留关闭原因；需要继续时复制为新草稿 |

经理可对编辑中的草稿直接完成校验并发布，不要求再走一次提交审核。审核和发布由同一人完成即可，不增加多级审批。

## 内容及编辑界面

项目的需求管理增加“草稿”入口及待审核数量。列表显示标题、作者／提交方式、状态、需求／工作项数量、校验问题数和更新时间；支持按状态、作者和关键词筛选。

草稿详情提供“需求与来源”“拓扑”“计划”三个视图，共用同一份服务端草稿。普通审核不要求编辑 JSON；保留 JSON 导入／导出作为辅助入口。

| 内容 | 必须支持的编辑 |
|---|---|
| 草稿说明 | 标题、输入材料摘要、Agent 的拆分理由、计划假设、待确认事项 |
| 需求 | 新增、修改、删除，拆分、合并，直接执行／工作项执行，特性、验收条件、候选／本期范围 |
| 来源 | 来源名称、正文、原编号、可选原版本及地址，条款增删，需求与条款的多对多落实范围，暂缓及原因 |
| 工作项 | 新增、修改、删除、调整归属，实际产出及估算；共享成果只保留一个执行对象 |
| 工作流 | 选择已有工作流并展开工作与依赖，查看变更后应用到草稿；展开后可编辑 |
| 拓扑 | 需求内部及跨需求关系、独立里程碑，图上或表单中增删连线，查看具体工作项端点 |
| 计划 | 有依据的工期、起止计划、最早开始及里程碑日期，按依赖预览排期，显示未知项和假设 |
| 人员 | Agent 不代选；人类可以填写负责人、协作者和验收人，也可以先留空 |

来源地址不应成为保存或发布的必要条件。手工说明、会议结论可凭来源名称和正文录入；系统内部修订独立标识，缺失的原始编号和版本不编造。填写地址时仍校验其格式。

工作流记录所采用的版本和展开结果。模板后续修改不静默改变审核中的方案；重新套用时展示差异，保护人工编辑。

## 编辑关系与拓扑规则

- 删除草稿需求时列出将移除的工作项、来源关联和依赖；仅删除草稿对象。移除对已有需求的引用，不删除正式需求。
- 拆分或合并需求时分配工作项与落实范围，保留稳定标识；不得重复生成共享工作。关系改接后重新校验，不能静默丢弃依赖或验收条件。
- 拓扑区分草稿新增对象与正式只读引用。已有需求、工作项及里程碑可作为依赖端点，必须属于同一项目。
- 连线表示真实的完成后开始；优先连接提供前置成果的具体工作项，不以原文顺序或共用条款推断依赖。
- 完整执行网络必须无环。需求汇总图中的双向关系可以表示分阶段协作，由工作项网络判断是否有效。
- 删除或排除节点后，悬空关系必须明确处理。不能为了让发布通过而自动取消前置条件。

首版支持新交付方案和对既有成果的引用、来源关联及依赖。不在草稿中修改既有正式对象的资料、计划或执行事实；对既有需求追加工作项、直接执行转拆分等变更提案后续扩展。

## 草稿保存与多人审核

- 服务端保存是正式草稿；浏览器本机缓存仅用于断网和输入恢复。换电脑、换有权限的审核者仍能读取已保存内容。
- 编辑自动保存，界面区分“保存中、已保存、保存失败”。失败保留输入并可重试；提交审核或发布必须针对已保存版本。
- 保存允许业务信息不完整，包括待补标题、验收条件、工期和待修复拓扑；结构错误、越权或跨项目引用仍拒绝。校验问题定位到具体对象和字段。
- 每次保存携带草稿版本。版本不一致时保留本地修改并展示差异，不以整包覆盖他人的版本；首版采用人工解决冲突，不做实时协同编辑。
- 保留 Agent 提交版本、当前版本及最终发布版本；记录操作者、时间和退回／关闭理由。自动保存不逐按键生成审核事项。
- 草稿有独立版本及列表刷新标识。保存草稿不触发正式项目分析版本变化；发布成功后才刷新正式视图。

## 校验与发布

草稿内可以预览“当前正式项目＋本草稿”的完整网络，明确标为方案预测；其他未发布草稿不参与这次计算。

| 校验结果 | 处理 |
|---|---|
| 新需求缺标题或验收条件；落实范围为空；标识冲突；悬空依赖；执行成环；无效日期；越权或跨项目引用 | 阻止发布，定位问题，保留草稿 |
| 缺人员、缺工期或计划；来源未关联；明确暂缓；估算带假设；可能重复的交付 | 提示审核，允许在符合业务约束时发布；不补造数据 |
| 正式对象、来源、所用模板或项目分析版本已变化 | 展示差异，刷新引用并重新预览，不盲目替换版本号 |

审核页展示本次将创建的对象、复用的正式对象、来源关联、依赖及计划差异，列出对现有项目预测的影响。依赖尚未纳入交付的候选需求时明确提示。

发布遵循以下规则：

1. 发布针对已保存的确切草稿版本和最新预览；任何修改都会使旧预览失效。
2. 首版整份发布。人类可先删除不采用的草稿内容或将来源条款暂缓，不做任意勾选部分发布及自动拆分依赖。
3. 特性、来源、需求、工作项、里程碑、关联、依赖及计划在一个事务中写入；同时写入发布回执并将草稿标为已发布。失败整批回滚。
4. 发布使用唯一批次 ID 和内容校验。同批次重试不重复创建；结果未知时先查询回执，核清前保留原请求并停止继续编辑发布内容。
5. 发布后返回草稿临时标识到正式对象 ID 的映射，页面可直接打开正式需求。Agent 在权限范围内也能查到人类发布后的结果。

已发布草稿不能再次发布。后续修改走现有正式编辑规则或新方案，不将旧草稿重新打开后重复创建。

## 权限与 MCP

项目成员可创建、编辑并提交自己的草稿；经理和管理员可审核项目内草稿、修改、退回、关闭和发布。普通成员只能读取自己的草稿，经理可读取本项目全部草稿。MCP 继承绑定账号权限。

拟新增 MCP：

| 工具 | 作用 |
|---|---|
| create_requirement_draft | 创建服务端草稿；请求标识防止网络重试创建重复草稿 |
| list_requirement_drafts / get_requirement_draft | 分页查询及读取内容、版本、审核状态和发布结果 |
| update_requirement_draft | 仅更新编辑中草稿，带版本保存，不写正式对象；待审核需先由人类退回 |
| preview_requirement_draft | 检查资料及完整网络，返回问题、影响及预览凭据 |
| submit_requirement_draft | 将指定版本提交给人类审核，返回系统内审核入口 |

Web 使用相同服务的 REST 接口，增加退回、关闭、发布及回执查询。创建、保存和提交需要可重试的请求标识，失败或结果未知不清空 Agent 的原请求。发布记录人类审核者；草稿发布结果按草稿访问权限读取，不限于最初创建它的账号。

“优先录入草稿”按默认工作方式实现：更新 skill，引导 Agent 保存并提交审核后报告草稿位置，不调用正式导入保存。首版不提供 MCP 发布工具，旧 MCP 直接写入工具保持兼容。

这不等于从权限上禁止所有直接写入。若要强制所有 Agent 变更经人审，应另设 Token 的“仅草稿写入”权限，并统一限制所有正式写入接口；不能只隐藏发布按钮。首版按“默认走草稿”实施。

## 验收场景

1. Agent 经 MCP 提交一份方案；另一台电脑上的经理可在系统中查看和继续编辑。
2. 草稿保存、校验和提交审核均不增加正式需求、工作量或改变交付预测。
3. LOG 的权限规则与查询接口／Mock 并行、联调后鉴权验证，可以在图上编辑并通过完整网络校验。
4. ORG 的粗条款可以保留、拆分或合并；共用审计成果只创建一次，来源范围和依赖仍正确。
5. 人类无需编辑 JSON，即可增删改需求及工作项、套用工作流、编辑拓扑和制定计划。
6. 没有人员、来源地址或完整计划时仍可保存草稿；满足内容和拓扑约束后可发布候选需求。
7. 删除、拆分、合并后出现的悬空引用与环路能定位并阻止发布。
8. 人工修改后，旧 Agent 请求及另一位审核者的旧版本不能覆盖；输入保留，能处理冲突。
9. 正式对象或模板在审核期间变化，旧预览不能发布，刷新后保留已有编辑。
10. 双击发布、超时重试、并发发布只生成一套正式对象；任一写入失败不留下半份结果。
11. 发布后默认候选，状态、实际进度和承诺不被自动推进；回执可供审核者与草稿作者核对。
12. 普通成员不能发布、修改他人草稿或引用无权项目；项目权限变更后立即生效。

首版不增加多级审批、实时协同、草稿互相依赖、自动消息通知或全面的正式数据变更审批。
