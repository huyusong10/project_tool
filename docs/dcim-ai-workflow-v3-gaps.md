# DCIM AI 工作流 V3.0：系统差距与改造建议

日期：2026-09-17。依据：[SDS 子文档中的工作流规则](https://ec-confluence.jereh.cn/pages/viewpage.action?pageId=6589992)、本次讨论及当前代码、MCP 实时数据。本文记录建议，系统功能改造尚未实施。

V3.0 的初始设计在 Phase0 完成：MPS → UX 与数据设计并行 → MDS 及接口基线 → 设计基线确认里程碑。需求阶段编写或更新 EPDS，核对已有设计、实现并验证。完整支持还需要两项主要改造：工作项可以直接归属特性或 Phase；Phase 的完成规则纳入适用的整体验证。跨特性继续使用依赖、联合验证工作和项目独立里程碑。

## 1. 当前模板与存量安排

DCIM 项目：`a9bf5f57-d7db-45b1-931a-e84ed336b805`。

| 模板 | 工作项与默认依赖 | 模板 ID |
|---|---|---|
| DCIM AI工作流V3.0（设计） | MPS → UX／数据设计并行 → MDS与接口基线 → 设计基线确认 | `a516c221-9d02-4ce1-b34b-0ca341bb2bd1` |
| DCIM AI工作流V3.0 | EPDS设计与前端开发 → 后端与数据实现 → 联调 → 功能测试 | `8bf70827-6bdd-453f-b532-7f54fe369652` |
| DCIM AI工作流V3.0（后端） | EPDS设计 → 后端与数据实现 → 功能测试 | `6342d5b1-2020-46d8-a161-5795b1882f85` |

Phase0 的 UX 与数据设计共同讨论，后端设计负责人提前参与，MDS 可以同步起草并在最后确认。当前设计模板中，里程碑直接依赖 MPS 和 MDS；UX、数据设计通过 MDS 汇入，不再要求四项全部直接连接里程碑。MDS 完成说明须引用适用的 UX、数据设计及接口契约版本，并记录一致性校核结果，不另设审批。数据设计作为 MDS 的组成或唯一引用来源，接口精确结构使用可定位版本的工程契约。

有界面需求由前端在“EPDS设计与前端开发”中编写或更新 EPDS，并完成前端实现，分类为 `development`；后端实现默认等待该项完成。无界面需求由后端负责“EPDS设计”，分类为 `analysis`。EPDS 继承 Phase0 的 UX、数据、MDS 与接口基线，展开本次功能的局部行为、差异、实现和验收，不重新决定公共设计。首项完成不代表需求完成，后续实现、适用联调和功能测试仍须执行。设计核对并入实际工作，不新增独立 UX、数据确认节点。真实联调、功能验收前核对接口基线与实现、环境一致，单元测试和契约检查可提前。

模板是默认骨架。纯后端有实际接口协作时添加联调；纯前端删去不适用的后端、数据工作。需求实现默认串行，只有具体工作已具备独立开展条件并明确约定时，才调整依赖为并行。无界面需求不安排前端、UX 或界面手册。裁剪后仍需验证真实结果，不增加条件分支引擎。

当前模板工作项工期必须是正整数。每项的 1 个工作日及偏移只是排期占位，应用时按范围重估，不能解释为交付承诺；里程碑为 0 日。模板描述已写明这一限制。前一轮实例新增工作保持未估算、未排期。[工期校验](D:/tools/project-manage/src/server/services.ts:665)

前一轮通过 MCP 建立三个 V3 模板，迁移 FUN-05～09 的五条已有 DES 设计记录，以及 FUN-05 Phase1 的 DCIM-162、163、164。Phase1 三需求保留原归属；FUN-09 复用原型工作；已有执行事实、人员、计划和外部依赖保留。项目默认仍为 V2.0；旧“需求与软件设计”模板被其他操作归档，保留该结果。

本轮按用户更新后的模板同步文档与 skills，以最新名称、节点和依赖为准。项目管理系统只读，模板更新不会自动覆盖实例。

| 对象 | 当前差异 |
|---|---|
| 模板与 Phase 说明文字 | 部分仍沿用旧模板名、“后端分析”及前后端并行说明，与最新模板图不一致 |
| FUN-05～09 的五条 Phase0 设计记录 | 里程碑仍直接依赖四项设计工作；新模板直接依赖 MPS、MDS |
| FUN-05 Phase1 的 DCIM-162、163、164 | 仍保留“前端实现（含设计核对）”与后端并行的安排；未迁移为新模板的 EPDS 首项与串行依赖 |

这些是配置与存量差异，不代表系统缺少新的流程引擎。后续若迁移，按实际工作项差异处理并保留执行事实，见 G5。

## 2. 现有能力可以继续使用

| 能力 | 在 V3.0 中的用法 | 证据与边界 |
|---|---|---|
| 特性、Phase、需求的组织与文档链接 | 特性持续维护 MPS、UX、数据设计、MDS 及接口契约；Phase0 组织初始设计，后续 Phase 写范围与整体验证目标；需求引用本次功能对应的设计 | `referenceLinks` 已支持多链接；无需建立一棵重复文档目录。[Phase 字段](D:/tools/project-manage/src/shared/feature-phases.ts:7) |
| 模板选择、工作项增删改、依赖调整 | 人选择合适骨架，再按实际工作裁剪 | 已执行工作保留历史，仅调整剩余工作；高适配性本身不是待开发功能。[工作项服务](D:/tools/project-manage/src/server/services.ts:1514) |
| 工作负责人、协作者、进展和返工 | Phase0 前端与 UX 结对，后端与数据人员共同设计；需求的后端工作包含数据实现，测试作为实际工作 | 不按角色强制拆工作项。[工作项字段](D:/tools/project-manage/src/server/schema.ts:182) |
| 模板里程碑、实际依赖和版本化文档链接 | Phase0 设计基线确认纳入接口基线，需求实现引用该成果；真实联调和功能验收前核对实现、契约及环境版本 | 复用现有里程碑，不新增审批引擎或每需求接口里程碑；里程碑标记不能代替设计完成说明与证据 |
| 跨需求依赖、项目独立里程碑 | 联合验证等待各特性的具体成果，验证完成后支撑交付里程碑 | 独立里程碑的 `requirementId` 可空，不需新增跨特性 Phase。[里程碑定义](D:/tools/project-manage/src/server/schema.ts:248) |

目前 `create_work_item`、模板应用和进展都需要需求 ID；Phase 完成只汇总需求。此前按用户授权复用 FUN-05～09 已有的 DES 设计承接记录组织 Phase0 工作，未新增占位业务需求。这是当前工具内的执行安排，直接归属和 Phase 验证规则仍是差距。

现有自动里程碑只检查直接前置工作是否完成，不会沿依赖链校验 UX、数据设计或证据；工作开始或完成命令不会自动校验接口契约、环境版本及验证证据。已有依赖和完成标准指导实际执行，不等于系统已经实现接口基线的自动检查。负责人在 MDS 完成说明及联调/测试记录中引用本轮契约和证据。[工作执行](D:/tools/project-manage/src/server/services.ts:1670)、[里程碑判定](D:/tools/project-manage/src/server/services/milestones.ts:17)

## 3. 差距与改造建议

### G1：一套工作项支持三种直接归属（首批）

现状：`work_items.requirement_id`、`progress_updates.requirement_id` 都是必填。权限、查询、路径分析也通过需求查找项目。[工作项](D:/tools/project-manage/src/server/schema.ts:187)、[进展](D:/tools/project-manage/src/server/schema.ts:272)、[权限](D:/tools/project-manage/src/server/authorization.ts:174)、[查询](D:/tools/project-manage/src/server/services/queries.ts:43)、[路径分析](D:/tools/project-manage/src/server/services/paths.ts:37)

为什么：初始设计工作应归 Phase0，后续公共设计维护可直接归特性，整体验证应归所属 Phase。长期借用“设计需求”“测试需求”会混入功能清单，也无法准确区分工作归属与成果引用。

建议怎么做：

- 保留现有工作项模型，增加特性、Phase 两种父级。每项只能有一个直接父级，项目与父级必须一致；返回值明确直接归属和从父级推导的特性、Phase，不把推导字段当成第二份归属。
- 进展、计划、实际日期、负责人、协作者、链接、版本和审计仍用一套机制。进展允许脱离需求，按工作项查所属项目，保留原事件内容和作者。
- 特性/Phase 工作由项目经理管理创建、归属、人员和计划；工作负责人及协作者沿用执行与追加进展权限。需求工作保留现有需求负责人权限。特性级设计负责人可以由 MDS 工作负责人表达，无须新增岗位或审批体系。
- 所有入口共同支持新归属：MCP、网页清单、关系图、进展表、甘特图、我的工作、人员并发、依赖分析和导出。工作量按工作项 ID 计一次，父级汇总不能与下属工作重复相加。
- 依赖端点支持直接用工作项 ID 解析项目和父级，不再要求新工作携带一个虚构需求 ID。仍使用现有循环检查、分析版本和预览提交机制。

验收：

| 场景 | 可观察结果 |
|---|---|
| 分别在特性、Phase、需求下新增工作，不填写人员和日期 | 都能保存；详情只显示一个直接父级；不产生占位需求 |
| 一次提交同时指定两个父级，或引用其他项目的父级 | 网页和 MCP 均拒绝，原数据不变 |
| 为三个层级的工作指定同一成员，再执行、记进展和完成 | 我的工作、人员并发、查询分页均找到三项；无重复计数；作者和时间可追溯 |
| 工作协作者追加进展，非参与成员尝试执行；普通成员尝试移动归属 | 前者按现有协作权限成功，后两者被拒绝；经理可管理；项目只读用户不能写入 |
| 特性设计工作 → 需求实现 → Phase 验证建立依赖并预览排期 | 三项进入同一依赖分析；循环被拒绝；未知工期保持未知；网页与 MCP 结果一致 |
| 移动、归档、删除包含新归属工作的对象 | 校验未完工作、依赖和历史；不留下孤立进展，也不静默删除执行事实 |

### G2：Phase 完成必须包含整体验证（首批）

现状：所有有效需求完成时，`phaseStatus()` 直接返回完成；完成日期取需求的最晚实际完成日。Phase 没有独立工作或验证条件。[状态计算](D:/tools/project-manage/src/shared/feature-phases.ts:15)、[完成日期](D:/tools/project-manage/src/shared/feature-phases.ts:32)

为什么：需求局部测试只能证明本次功能。跨需求场景、组合权限和受影响回归仍可能失败，需求全部完成不能证明功能 Phase 可交付。Phase0 则需要证明设计一致、可实现及接口契约明确，不能套用运行软件的验收条件。

建议怎么做：

- 继续用 Phase 的 `scope`、`note` 和链接记录范围、整体验证目标、必要环境与数据前提；不用新增一套 Phase 文档。
- Phase 下安排验证工作，记录负责人、计划和结果。增加一个轻量的“必要验证工作”引用列表，关联同项目已有工作 ID；至少指定一项，不能从名称含“测试”或里程碑名称自动推断。Phase0 可引用包含设计一致性及契约校核的 MDS 工作，不再造重复的验收工作；功能 Phase 引用实际集成与回归工作。
- Phase 完成需同时满足：本批有效需求完成、本级有效工作完成、必要验证工作全部通过。对验证工作，完成表示已通过，完成说明或证据链接必须指出验证范围、版本和结果，运行验证还须说明环境；失败保持未完成并记录问题。取消验证工作不等于通过，缺少有效验证时不能完成。
- Phase0 的设计基线确认包含 MPS、适用的 UX/数据设计、MDS 和可定位的接口契约相互一致。按当前模板，里程碑直接依赖 MPS、MDS，UX、数据设计与契约的校核证据进入 MDS 完成条件；不要求运行软件 E2E。接口契约在本轮实现前明确，真实接口联调及功能验收前核对实现、契约和环境版本；单元测试与契约检查可以提前。后续接口增量更新原基线并通知受影响调用方，不反复重启整个 Phase0。
- 需求测试仍保留，范围是主要功能、改动边界异常、接口/数据一致性及涉及的权限、数据完整性。Phase 验证可以分批开展；最后一项必要验证通过后再完成 Phase。
- Phase 状态、完成日期、进度和逾期从同一份事实计算。保留“需求完成数”，另展示验证工作情况；不能显示需求 100% 就把 Phase 标为 100% 完成。

验收：

| 场景 | 可观察结果 |
|---|---|
| 本批需求完成，整体验证未开始或失败 | 需求保留完成事实；Phase 显示进行中及未通过的验证 |
| 删除或取消唯一的必要验证，或列表为空 | Phase 不会因此自动完成，页面明确缺少整体验证 |
| 真实验证通过并记录证据 | 必要工作均完成后 Phase 完成；完成日期包含实际验证日期；所有视图口径一致 |
| Phase0 完成设计，但接口契约与 UX/数据设计冲突 | MDS 校核未通过，设计基线不能确认；修正并记录版本后才满足条件 |
| Phase0 的设计及契约校核通过，尚无可运行软件 | 可完成设计批次；不会被要求虚构功能测试结果 |
| 功能测试使用了与基线不一致的接口版本 | 记录差异并同步基线或修正实现；不能把该结果直接记为约定范围通过 |
| 功能仅使用 Mock 演示 | 可记录阶段性结果，不能以此完成要求真实联动的验证工作 |
| 重开本级验证，或本批需求返工 | Phase 恢复进行中；上轮完成及测试记录仍可查询；复测后产生本轮完成事实 |
| 部分需求被取消，已完成需求被归档 | 取消项不计入；归档完成贡献保留；验证条件不被取消需求绕过 |

### G3：一个联合验证工作项供多个特性使用，返工后明确本轮结果（首批）

现状：跨特性可以通过需求/工作项依赖及项目独立里程碑连接；普通链接可以引用同一份证据，但不参与 Phase 完成计算。已达成的独立里程碑不会因上游返工自动撤销；现有 `milestone_command(reopen)` 可以重开，并改为人工确认。[自动达成](D:/tools/project-manage/src/server/services/milestones.ts:16)、[重开](D:/tools/project-manage/src/server/services/milestones.ts:22)

为什么：复制测试工作会重复安排和统计。另一方面，旧“已达成”标记或同一个报告链接不能自动证明变更后的功能仍通过。

建议怎么做：

- 联合验证只归属牵头特性的 Phase，同一工作项可以多轮执行。其他特性的 Phase 在 G2 的必要验证列表引用同一个工作 ID，参与者进入同一工作的协作者列表；不复制工作、不增加跨特性 Phase。
- 验证等待具体需求或实现工作，不默认等待整个 Phase，避免“Phase 等验证、验证等 Phase”。需要演示、发布或客户交付时，再连接项目独立里程碑；里程碑只表示结果。
- 证据存在一次：测试工作的完成记录和链接保存范围、版本/环境及结果；各 Phase 展示该工作的当前结果和本轮完成记录。链接只是资料引用，不能单独当作通过事实。
- 只有变化实际影响所引用成果或验证范围时，才提示受影响的联合验证和交付里程碑；不把所有改名、排期或备注变化都纳入。责任人复核后，使用现有返工/重开动作处理受影响项；项目经理重开已达成的独立里程碑。保留上轮历史，不默认把所有相邻测试都重做。
- 本轮适用性未复核时，显示待复核提示，不沿用旧通过结果完成 Phase 或宣布当前交付。提示基于进展/返工记录及必要的有效性标记，不增加流程主状态，也不是所有变更必经的审批；继续使用现有返工、重开和完成动作。

验收：用 ORG 的租户创建、IAM 的管理员初始化与登录、LOG 的操作记录查询建立一次联合验证。

1. 联合验证只归属 ORG 的一个 Phase，IAM、LOG 引用同一 ID。系统只计一份人员投入；三个 Phase 都能打开同一结果。
2. 任一必要成果未就绪，不能把验证标为真实通过；其他无关需求不阻止这次验证开展。
3. 联合验证通过后，各 Phase 仍须满足自己的需求和本级工作条件；项目里程碑只有满足自身前置后才能达成。
4. IAM 的相关功能返工后，旧报告和里程碑历史仍可见，但本轮验证显示待复核。重开验证与里程碑后，各引用方立即反映未通过；复测完成才重新满足验证条件。
5. 复核确认某项变更不影响该验证时，记录原因，保留既有证据；不重开无关工作。

### G4：模板说明适用层级，允许估算未知（后续按需）

现状：模板只能应用到需求，`applyTemplateInternal()` 按需求 ID 创建工作；模板工期不能为空。阶段分类 `workStage` 已存在，也允许并行阶段。[模板应用](D:/tools/project-manage/src/server/services.ts:922)、[模板约束](D:/tools/project-manage/src/shared/contracts.ts:309)、[阶段计算](D:/tools/project-manage/src/shared/execution-stage.ts:21)

为什么：特性设计和 Phase 验证落地后，用户需要辨认模板放在哪里；占位工期也不应长期进入预测。需求类型适配已能通过选择和裁剪完成，无须开发自动分流。

建议怎么做：

- G1/G2 先支持手动创建即可。后续复用现有模板增加一个适用层级字段；旧模板默认需求级。应用入口校验父级，不新增三套模板系统。
- 允许模板工期未知，实例未估算时保持未估算；只有具备工期和起算条件才产生计划。保留现有已知工期模板行为，不把未知写成 0 日里程碑。
- 继续使用现有阶段分类：Phase0 的 MPS、UX、数据、MDS 设计可用 `analysis`，功能 Phase 验证用 `testing`。“EPDS设计与前端开发”及后端实现使用 `development`；后端模板的“EPDS设计”用 `analysis`。分类用于查看事实，不要求每个需求必须经过全部分类。
- 重选模板只处理满足原系统条件的未执行需求；已执行需求只补剩余工作。模板更新不追溯覆盖实例。

验收：需求级模板不能误套到 Phase；新增适用层级后可在对应父级生成原有工作项模型。未估算模板能保存且不会生成可信交付日。分别用有界面、纯后端、纯前端三例验证裁剪：均无多余角色工作，均保留功能测试，已有约定允许的并行可正常展示。重选或升级模板不覆盖既有执行记录。

### G5：存量数据保留历史，按需迁移（首批）

现状：历史设计工作已经以需求形式承接；旧 Phase 的完成含义是需求全部完成。工作项当前不能直接换父级。[归属限制](D:/tools/project-manage/src/server/services/editor-entities.ts:36)、[Phase 旧规则](D:/tools/project-manage/src/shared/feature-phases.ts:15)

为什么：直接改表后把旧完成状态解释为“整体验证通过”，会产生不存在的测试事实。重建需求或工作项还会丢失链接、依赖和历史。

建议怎么做：

- 数据结构迁移先让所有旧工作保持需求归属，保留 ID、状态、人员、计划、实际日期、依赖和事件；不批量替换 V1/V2 模板。
- 旧 Phase 完成记录标明按旧规则形成、整体验证未记录；历史完成继续可查，不能展示成 V3 已通过。是否继续执行、补验证或纳入 V3，由项目经理按实际范围处理。
- 未完成设计/验证工作需要迁移时，提供一次有预览和版本检查的移归属操作；保留工作 ID，更新父级查询与汇总，记录原父级、目标父级和原因。已完成记录默认保留原处，不为整齐批量迁移。
- 存量流程按工作项差异迁移，保留执行记录与外部依赖。若记录仍保留旧模板来源，用说明标明当前采用的流程，不为改模板标签而重建工作。后续需要显示当前流程版本时，支持保留原模板来源的关联更新，并明确这不会自动重置工作或重新排期。
- 原“设计需求”不删除历史。剩余工作移出后，按事实处理该需求；不能由系统擅自补完成日期或将它当成功能交付。需要追溯时保留原记录链接。

验收：在包含进行中、完成、取消、归档和返工记录的数据副本上迁移。迁移前后工作 ID、执行事件、真实日期、负责人和有效依赖数量可核对；旧 Phase 没有新增“测试通过”事件。移动剩余设计工作后，新旧父级统计正确且不重复；版本冲突整批回滚。若更新当前流程关联，原模板来源及工作记录仍可查，不触发重置或重新排期；V2 存量需求与新建 V3 需求可并存。
