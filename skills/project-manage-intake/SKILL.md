# 项目需求录入与交付

把输入变成可以明确范围、安排执行、核对验收的项目记录。粒度服从实际交付，不要求所有模块采用相同拆分方式。使用当前已连接的 project-manage MCP，工具名前缀可能不同。

## 判断记录放在哪里

| 对象 | 判断依据 | 用法 |
|---|---|---|
| 来源文档／条款 | 输入究竟说了什么 | 保存原文、版本、章节、原编号；与需求多对多关联 |
| 需求 | 能单独确定交付范围、负责人和验收结论 | 可以很小并直接执行，也可以分解工作项 |
| 工作项 | 为某项交付实际完成的一份工作 | 按成果、分工或就绪条件拆；完成后仍由需求验收 |
| 分组 | 项目内稳定的整理维度 | 如 LOG、ORG；单层、可选，不承诺独立进度和工期 |
| 标签 | 阶段、部署侧等交叉维度 | 如基础准备、边缘、中心、建议拆分；优先复用已有写法 |
| 独立里程碑 | 有独立意义的阶段出口或外部条件 | 如环境已交付、上线窗口；通过依赖参与计划 |
| 问题 | 需要跟踪处理的障碍或未决事项 | 记录影响和处理责任，必要时关联阻塞对象 |
| 模板 | 多次出现、已认可的执行流程 | 复用实际工作及先后关系，不为每项需求套同一组岗位 |

- 文档章节、原始编号、工作岗位、页面和接口都不自动等于一个需求。
- 小需求能独立交付时直接执行，不再创建同名工作项。粗条款可对应多个需求，多个条款也可合成一个需求。
- 同一成果只有一个执行归属。其他需求复用来源关联或依赖，不复制工作量。
- 共用来源表示追溯关系；依赖表示前置条件。不能把“来自同一条款”自动变成先后顺序。

## 读取上下文

1. 确认已连接环境、目标项目与当前权限。用户已指定的项目直接定位，确有歧义再询问；不按标题自动新建同名项目。
2. 发现工具及输入 schema。导入需要 preview_requirement_import、apply_requirement_import、get_requirement_import_receipt。缺少时先准备本地 JSON 并说明能力缺口，不把来源塞进标题假装完成导入。不要为此自行换环境、部署服务或写数据库。
3. 用 query_requirements、list_work_items 定位已有交付和执行工作，按需读取详情、分组、标签、来源和成员。检查未排期缺口时不加日期筛选，直接执行需求也要检查。安排执行时再读模板、完整路径、交付承诺及人员并发。
4. 读取原文及版本。区分原文事实、建议拆分和未决事项；保留原 referenceUrl，不从旧链接推断条款。

工具选择、契约和提交步骤见 [MCP 操作参考](references/mcp-workflows.md)。按需阅读，不必为单个小需求加载全部接口。

分页筛选、历史快照、开工条件、局部图及 SVG 导出见 [查询与拓扑](references/queries-and-graphs.md)。旧连接缺少新查询时使用已发现的读取工具，不把第一页、近期记录或局部图当成完整项目。

## 整理交付安排

先形成简短映射：`来源 → 交付需求 → 本次落实范围 → 执行方式 → 验收条件`。范围写明本次做到哪里，必要时说明留待何处；验收条件写可观察的结果和证据。

| 输入情况 | 处理 |
|---|---|
| 一条可独立验证的小修改 | 一个直接执行需求 |
| 大条款混有多个可分别验收的结果 | 拆成多个需求，各自填写来源范围 |
| 多个条款共同定义同一次交付 | 合成一个需求，关联所有必要条款 |
| 阶段不同，但最后共同验收 | 同一需求下分工作项；只给真正前置的工作加依赖 |
| 只交来原文，尚未决定安排 | 只录来源，或建立明确标注的候选建议 |
| 用户明确暂缓某一范围 | 填写原因；只暂缓条款的一部分时，摘出该部分并明确章节／范围，避免标记整条功能都延期 |

来源 key 首次确定后保持稳定，版本更新沿用。已有来源以系统目录的 key 为准，不用案例 key 替换旧 key。原编号可以重复，不能单独用它匹配；标题或内容改变时也不能重新生成 key。已有对象用系统 ID，包内新对象用稳定 key。禁止标题模糊匹配后覆盖。

新增建议默认 candidate，标签或背景注明“建议拆分”。低优先级不自动等于暂缓；来源 P0/P1 保存在来源信息。系统处理优先级由交付风险和路径计算，不靠兼容字段 priority 强行指定。

## 保存与核对

- 用户已授权录入时，完成整理和服务端预览后继续保存；不再重复请求同一授权。用户只要求方案或预览时，交付草稿即可。
- 导入包默认 complete=false。只有实际核对整篇文档的相关条款已完整整理，才声明完整导入。
- 预览核对重复编号、已有匹配、未关联条款、验收条件、来源差异和依赖影响。已有成果优先关联；确实需要另建一份交付时，才显式选择新增。
- 预览后的修改需要重新预览。提交前保存完整请求和批次 ID；结果未知先查回执，重试保持原批次和内容，不能换批次碰运气。
- 保存后回读正式 ID、来源范围、分组标签和执行方式。分别核对未关联、候选、正式交付、已验收、待核对和暂缓状态。
- 来源版本变化不会自动撤销验收。读新旧内容，核对范围后保存当前来源修订 ID；已完成交付的新增工作另行安排或按授权返工，不覆盖历史。

## 用系统安排和推进工作

仅在本次任务包含安排或推进时执行对应操作。不要为了“用全功能”批量制造记录。

| 决策 | 使用方式 |
|---|---|
| 谁做、谁验收 | 需求负责人负责交付，工作项负责人负责执行；多方参与用真实成员 ID。岗位建议不能当成人员账号。验收人按用户指定或系统经理规则处理 |
| 是否本期交付 | 明确范围后从候选纳入 committed；候选不能直接开始。普通录入不自动代表承诺、开工或验收 |
| 何时能完成 | 对实际执行对象填写有依据的工期、计划、最早开始或预测。人员、日期、工期未知就留空，不填今日、默认一天或平均分摊 |
| 如何建立依赖 | 只连接真实的完成后开始条件。需要“接口就绪”就引用该工作项，避免等待整个上游需求验收。双方分阶段协作可以使需求汇总图双向，但完整执行网络必须无环 |
| 如何排期 | 先预览依赖／模板排期，检查完整项目影响和人员并发，再保存。工期、计划、实际日期和预测分别维护；筛选结果不能代替完整网络预测 |
| 如何说明拆分与影响 | 用 get_path_graph 查看需求内部或上下游，需要交付图时导出 SVG，并说明省略范围。自动布局不保存团队坐标；修改布局前读取完整位置并合并 |
| 如何保存承诺 | 用户明确要求记录交付承诺或确认基线时，在项目批次中写入 changes.commitment，保存不可变快照。仅纳入本期范围不自动创建承诺；后续变更写原因，比较首次与最近承诺 |
| 做到一半才拆分 | 用共享实体批次将直接需求转成工作项执行，只拆剩余工作，保留基线、历史及来源；不删除重建，不把原百分比复制到每个子工作 |
| 如何推进 | 用开始、进展、阻塞、解阻、完成、提交验收、验收／返工命令。工作项全部完成不等于需求已验收；不能通过通用编辑伪造状态或实际日期 |
| 如何处理障碍 | 简单延期不必造问题。确有障碍时说明阻塞原因；需要跨人处理时关联问题、协调人、下次核对日或有依据的解阻预测 |
| 如何发现安排缺口 | 合看来源未关联／待核对、需求准备度、行动项、路径风险和人员并发。未知预测就报告待确认；条款关联率、工作项完成率不能解释为整篇文档交付率 |

普通负责人只能维护权限内的执行和自己的来源范围；经理负责分组、来源维护、导入、范围和受控纠错。权限不足时保留草稿并说明缺少的权限，不改账号角色绕过。

## 案例与交付结果

不同粒度、跨阶段协作、共享成果和版本变更见 [LOG／ORG 案例](references/examples.md)。可改编 JSON 为 [LOG 选摘](assets/log-intake.json) 和 [ORG 选摘](assets/org-intake.json)，均为候选建议，没有真实人员和排期；不要把案例当成本次项目事实直接导入。

完成后简要报告：环境和项目、已保存／仅预览、创建与复用数量、条款覆盖边界、真正阻碍安排的问题、批次与正式对象链接。附本次 JSON 或回执位置；不要把草稿中的临时 key 当成正式系统 ID。
