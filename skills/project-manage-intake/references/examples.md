# 案例：不同粒度的需求如何录入

以下依据 2026-09-10 已读取的历史版本，拆分与安排均为建议。使用时重新核对当前版本、已有成果和用户范围；JSON 是选摘示范，不是完整导入，也不是获准执行的排期。

来源：[LOG v24 对应页面](https://ecc.jereh.cn/pages/viewpage.action?pageId=6595117)、[ORG v18 对应页面](https://ecc.jereh.cn/pages/viewpage.action?pageId=10423063)。页面可能已更新，案例仍以所标历史版本为准。

## 1. 已经足够细：直接执行

输入：“查询页的重置按钮清空全部筛选项，保留用户当前租户范围。”

建一个候选需求“查询条件重置符合租户范围”，executionMode 为 direct。验收条件写“清空业务筛选条件后回到默认列表；租户边界仍生效；结果与重新进入页面一致”。人员、排期未给出则留空。

没有正式来源文档时，不造来源 URL、版本或章节。把用户描述放在 background，已有相关条款就关联明确范围。不再建同名工作项，也不强制建立前端、后端、测试三份任务。

## 2. LOG：同一需求跨阶段执行

原文把日志查询、权限隔离、敏感信息和防篡改列为不同功能。Phase 1 明确规则和样例，Phase 2 实现各入口并验证；Phase 1 完成不代表整项权限需求验收。

| 建议交付 | 工作项 | 来源及范围 |
|---|---|---|
| 日志查询 | 查询接口、页面 Mock、接口页面联调 | LOG-006；组合筛选、分页和详情 |
| 日志权限与租户隔离 | 规则与拒绝样例、全部调用入口鉴权验证 | LOG-008；先给下游规则，再完成整体隔离验收 |
| 日志时间统一 | 直接执行，之后确有分工再拆 | 第一条 LOG-013；原始事件时间及展示时区 |

只连实际就绪条件：

```text
权限规则 ──→ 查询接口 ──┐
      └──→ 页面 Mock ──┴──→ 接口页面联调 ──→ 全部入口鉴权验证
```

权限和查询在需求汇总图中可能互有方向，工作项网络仍无环。不能改成“权限全部验收后才开始查询，查询全部验收后才开始权限验证”。

分组为 LOG；基础准备、功能开发、边缘、中心用标签。同一需求跨阶段可用多个标签。规则工作没有独立对外承诺时用工作项即可；用户明确把“规则基线发布”作为独立交付后，再考虑单独需求或里程碑。

两条 DCIM‑LOG‑013 分别为时间统一和自身监控。案例用 f-013-time、f-013-health 区分 key，保留相同原编号。为展示暂缓功能，案例约定“本次暂缓自身监控”并填原因；现实中不能仅凭 P1 自动决定暂缓。

可运行示例：[log-intake.json](../assets/log-intake.json)。3 个候选需求、5 个工作项；一条来源既可关联需求范围，又可引用为工作项出处，执行量仍只算实际工作。

## 3. ORG：粗条款拆出多个交付

ORG 原文只有租户、站点、位置三条大功能，但混有生命周期、纳管、资源归属和同步。按可单独验收的范围拆，不要求与 LOG 的功能数量或岗位划分一致。

| 建议交付 | 关联来源 | 本次落实范围 |
|---|---|---|
| 租户资料维护与查询 | 功能 ORG-001 | 资料、列表、详情与派生统计；其他生命周期操作另有归属 |
| 租户禁用删除及访问失效 | 功能 ORG-001、安全 ORG-001 | 禁用／删除前置检查、访问失效、历史保留 |
| 站点创建与边缘纳管 | 功能 ORG-002 | 中心生成 ID、边缘手工配置、平台维护与租户只读 |
| 站点归属变更 | 功能 ORG-001、ORG-002，安全 ORG-001、一致性 ORG-004 | 唯一入口、前置检查、单一归属事实源、级联禁用及审计 |
| 边缘位置树管理 | 功能 ORG-003、一致性 ORG-004 | 站点归属、防环、层级校验、资产迁移检查 |
| 边缘与中心资源同步 | 一致性 ORG-004、审计协同验收 | 资源同步、补传、事件产生与交付 |

“租户侧分配站点”和“站点侧变更归属”复用同一份交付，不能各排一次。归属变更可拆“前置检查”“归属切换与失效”“变更验证”；其余先直接执行，出现实际分工后再拆。

功能 ORG-001 与安全 ORG-001 也重复编号。key 使用 functional-001、quality-security 区分，不能去掉质量条款或覆盖功能条款。

可运行示例：[org-intake.json](../assets/org-intake.json)。6 个 ORG 候选交付，加 1 个 LOG 接入共享交付。只给归属变更内部工作建立明确依赖，其余不因来源关联而自动连线。

## 4. 跨模块共享成果只安排一次

ORG 产生并交付带对象锚定、字段快照、request_id 的审计事件；LOG 接入、存储、查询和留存。把 ORG“审计协同验收”和 LOG“多源日志采集和接入”关联到同一份 LOG 接入交付，写清两边责任。

若已有 LOG 接入需求，将案例 log-ingestion 改为 action=link，existingId 填真实需求 ID、workItems 留空，核对原范围后复用。不再为 ORG 建一套日志存储／查询工作，也不把整个 LOG 平台列为 ORG 交付责任。

共享成果要有真实范围。引用同一条安全规则但各模块仍需独立实现的工作，不能为了减少数量而合成含糊的“公共安全”。

## 5. 未决口径、版本变化和后续排期

- LOG 自动清理依赖留存期限口径统一。只暂缓“启用自动清理”；归档、恢复、法务保留可以独立安排。需要协调口径时建立问题，不虚构期限或承诺日期。
- 假设 ORG 后续版本修改归属变更的前置检查：沿用原 document/clause key，导入新原文，核对受影响需求。既有验收不自动失效；新增范围按用户决定建立增量需求或返工，保留旧关联修订。
- 直接执行到 30% 后要分给后端和前端：读取版本和完整路径，同一实体批次切换 work_items 并创建剩余工作。保留 30% 基线，不把两个新工作项各填 30%，不造已完成任务。
- 用户给出人员、估算和目标后，核对成员、并发与前置，预览全项目影响。范围确认后纳入 committed；明确确认基线时另保存交付承诺。源文档 P0 不自动代表系统 P0，候选前置影响正式交付时仍需查看完整网络风险。

分别报告“导入多少条款”“哪些范围已安排”“哪些关联需求已验收”。“本次选摘 5 条，安排 4 条、暂缓 1 条”不能写成“整篇文档完成 80%”。

## 6. 用新增查询检查导入结果

用户说：“ORG 已经录过一部分，补上缺的，再说明与 LOG 的关系。”

先用 query_requirements 分别按“归属”“日志接入”定位已有交付，按页读完候选结果，再用来源目录和 get_requirement 核对范围。命中同名只说明需要核对，不能直接覆盖；确认已存在的 LOG 接入用 action=link。

保存后，用 query_requirements 检查候选直接需求，用 list_work_items({projectId,active:true,unassigned:true}) 检查未分派的执行工作。两类检查都不加日期筛选，因此人员和排期仍为空的案例不会从检查中消失。候选待安排是导入结果，不是逾期或已开工。

用 get_path_graph 的 ORG 需求内部视图说明落实范围及实际前置；需要给用户看图时导出 SVG，并报告省略的节点。跨模块来源关联不一定是依赖，没有真实先后条件就不为连成一张图而加线。

用户再问“之前谁更新过联调”：用 list_progress_updates 按真实工作项 ID 查历史，翻页保留 snapshot。主负责人、协作者和进展发布者分别读取，不从最后一条进展推断负责人。
