# 案例：保留原始需求，明确工作与拓扑

以下依据 LOG v24、ORG v18 的已知内容整理，全部为建议，不是排期承诺。案例包已包含必要原始需求摘录，无需查找原文。人员和计划日期留空，由实际项目补充。

## LOG：同一需求跨阶段协作

保留“日志查询”“日志权限与租户隔离”“日志时间统一”三个可分别验证的原始需求。前两个分解工作，时间统一先直接执行。

| 需求 | 工作项 | 验收范围 |
|---|---|---|
| 日志查询 | 查询接口、页面 Mock、接口页面联调 | 组合筛选、分页和详情 |
| 日志权限与租户隔离 | 权限规则与拒绝样例、鉴权验证 | 各调用入口遵守授权及租户边界 |
| 日志时间统一 | 直接执行 | 原始事件时间及展示时区一致 |

保存工作项拓扑：

```text
权限规则 ──→ 查询接口 ──┐
      └──→ 页面 Mock ──┴──→ 联调 ──→ 鉴权验证
```

接口和 Mock 并行；权限规则先供查询使用，查询联调后再验证鉴权。两个需求在汇总图中互有方向，完整执行网络仍无环。不能改成两个需求整体互等完成。

两条原编号 LOG-013 分别代表时间统一与自身监控，用 f-013-time、f-013-health 区分 key。自身监控在示例中选择跳过，原文仍留在草稿中。

assets/log-intake.json 包含 3 个需求、5 个工作项、5 条依赖。分组为 LOG，阶段和部署侧写入需求说明。

## ORG：按需要保留、拆分与合并

原始功能需求按租户、站点、位置组织，同时涉及访问控制、资源同步和审计。

默认可保留三个原始需求，将资料维护、禁用、删除等操作分为工作项。只有实际要分别交付和验收时，才进一步拆开；不要仅因为一条内容长就增加需求数量。

assets/org-intake.json 演示“这些范围需要分别验收”的一种拆法：

| 建议交付 | 对应原始要求 |
|---|---|
| 租户资料维护与查询 | 租户管理中的资料及查询 |
| 租户禁用删除及访问失效 | 租户生命周期和安全要求 |
| 站点创建与边缘纳管 | 站点管理中的创建及纳管 |
| 站点归属变更 | 租户／站点需求中的归属要求，合并为一个交付 |
| 边缘位置树管理 | 位置管理及一致性要求 |
| 边缘与中心资源同步 | 同步与审计协同要求 |
| 公共日志接入 | ORG 的审计交付与 LOG 的日志接入，复用一个成果 |

“租户侧分配站点”和“站点侧变更归属”不能重复安排。归属变更拆为前置检查、归属切换与失效、变更验证，并保存顺序依赖；其他需求在分工明确前直接执行，不因共用原文而互相加线。

公共日志接入已有系统需求时，草稿中的 log-ingestion 直接复用其真实 ID；需要修改说明时使用 action=update 和 expectedVersion。ORG 负责产生并交付审计事件，LOG 负责接入；不要各建一套日志存储工作。

## 草稿使用

两个 JSON 使用 formatVersion=2。原文、编号和版本直接保存在需求说明中；工作项和依赖随需求导入。来源链接未知时留空。跳过项保留在草稿中，保存时不创建需求。

制定计划时，先检查真实前置与完整路径，再根据给定起点、目标和工期预览。没有这些依据时展示相对顺序及待确认估算；负责人和协作者由人类安排。
